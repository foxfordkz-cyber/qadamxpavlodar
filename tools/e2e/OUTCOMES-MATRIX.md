## Независимый эталон

[reference/outcomes-cases.json](reference/outcomes-cases.json) — небольшие синтетические
смысловые примеры с явно записанными входами и ожиданиями. Это **не** готовый
`OutcomeVariantInput`, не ответ API и не fixture `analyzeZone`. Сумма 300000 KZT —
арифметический пример, а не цена Павлодара. Отдельно сохранены точные дроби, чтобы
не закреплять случайное округление интерфейса.

В будущем тесте считать ожидаемое независимо:

```text
expectedTrees = sum(quantity * y3Pct / 100 for tree rows only)
unitCost = totalKzt / expectedTrees
           только при полной tree-only смете за 3 года и expectedTrees > 0
assessed = alive + dead
inspectionCoverage = inspected / total * 100
assessmentCoverage = assessed / total * 100
survivalAmongAssessed = alive / assessed * 100, если assessed > 0
wholeCohortSurvival = alive / total * 100, только если assessed == total > 0
differencePp = wholeCohortSurvival - expectedAlive / total * 100
              только для совпавшей годовщины и полного установленного состояния
```

Не импортировать production `calculateOutcomeVariant`, `compareOutcomeForecast` или
`costEstimate` как единственный oracle. Допустимо вызвать production-функцию как
**объект проверки**, сравнивая с ручной арифметикой. Сверка UI с ответом API дополняет,
но не заменяет независимый пример: одинаковая ошибка в UI и API не должна пройти.

Для интеграции построить согласованный ввод `analyzeZone(careYears: 3)` из отдельного
маленького seed: известные виды, ставки и площадь. Рассчитать material/prep/work/care/
reserve вручную по утверждённым правилам и затем сверить UI и API. Нельзя подставить
произвольный total в analysis, подавить `cost_mismatch` или менять expected под ответ.
Нельзя сначала рассчитать смешанную смету, а потом удалить цветы из знаменателя.

Числовая проверка сохраняет дробные ожидания и null до отображения; проверка UI
учитывает только согласованное округление и RU/KK-разделители. Точность вывода пока
не задана контрактом: её нужно закрепить по готовому интерфейсу, не придумывать сейчас.

## Осмотры, сохранение и исходный прогноз

Базовая партия P4 — четыре зарегистрированных дерева с подтверждённой посадкой
2023-10-30. Прогноз захвачен до посадки; y1/y2/y3 = 90/80/75%, `asOf=2026-10-30`.
Это искусственная демонстрационная история, а не историческая проверка модели.
Фиксированный `asOf` относится к контрольным примерам. Настоящий API берёт дату
с сервера: seed для годовщин строить относительно неё, будущий осмотр — на следующий
день. Не подменять серверный `asOf` произвольной датой клиента ради прохождения теста.
Ссылки на доказательства положительных примеров должны вести к реально созданным
и принятым отчётам из изолированного seed; строка с придуманным id доказательством не является.

## Условия подключения исполняемых тестов

1. Подтверждён merge #16: `git fetch origin`, новая `codex/outcomes-e2e` от свежей
   `origin/codex/coordinator`. Если ветка уже есть, проверить её историю и использовать
   обычный merge; не сбрасывать и не переписывать чужие коммиты.
2. Получены влитый контракт, маршруты/DTO API, UI с доступными текстами/ролями,
   правила записи по ролям, версии и идемпотентность, формат дат/округления.
3. Подготовлен изолированный seed с реестром, принятыми отчётами и подтверждениями;
   смысловые примеры превращены в валидный вход без подгонки чисел. Позитивные осмотры
   имеют настоящие разрешённые связи в seed. Существующую рабочую базу не использовать.
4. Подключать готовые срезы в обычные mock/API проекты; не создавать набор всегда
   skipped и не выдавать план за проверенное поведение. Реальные дефекты остаются failing.
5. Согласовать недостающие решения API с автором: write-роли, URL, ответы ошибок,
   ключ повторного сохранения, конфликт версий, допустимость пустой партии. Не менять apps.

## Финальная приёмка и сборка для защиты

После вливания всех согласованных PR зафиксировать SHA и чистое состояние. Полный mock
и API на новой изолированной базе должны относиться к **одному SHA**; записать раздельно
passed/failed/skipped/fixme, версии среды и причины каждого пропуска. Старые результаты
или предварительная проверка ветки не заменяют прогон интегрированного коммита.

До сценария защиты согласовать с пользователем **конкретную Docker-сборку**: исходный
SHA, image IDs/digests frontend/backend, способ сборки из чистого checkout этого SHA,
адрес :8080, безопасную тестовую конфигурацию и seed. Одной подписи «latest» или
произвольного revision-label недостаточно для доказательства происхождения. При
несовпадении SHA/образов сборку не считать проверенной. Не печатать docker inspect/env
целиком: конфигурация может содержать секреты.

Короткий сценарий на согласованной сборке: вход специалиста → зона → сравнение
сопоставимых tree-only вариантов → неизвестная/смешанная цена без ложного «лучший» →
исходный прогноз → частичный осмотр с двумя отдельными процентами → сохранение и reload →
переключение Рус/Қаз → 375 px без перекрытия → запрет записи для просмотра → выход без
прежнего имени/роли. Использовать демо-данные и не выдавать их за полевой факт.

Вывод о защите разделяет: функциональность приложения; новые outcomes; известные
дефекты; API/Docker/настольный Word, которые не проверены. Если API или Docker
недоступны, записать точную проверенную причину, SHA и невыполненные сценарии. Mock
не заменяет API; доступный локальный API не заменяет Docker.
