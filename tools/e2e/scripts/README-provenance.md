# Происхождение отчётов и снимков

Каждый `scripts/run.mjs` получает новый UUID. В `playwright-report/runs/<profile>.json` записываются полный Git SHA, dirty-флаг, URL без параметров, время, завершение, exit code и фактические Node/Playwright/workers/retries. Завершённые безопасные результаты сохраняются по UUID в `playwright-report/history`; старый запуск не заменяет новый.

Снимок для архива создаётся только общей функцией `support/helpers.ts` после проверки готового интерфейса. Для лаборатории необходимы завершённый расчёт и видимый план, для Outcomes — завершённая загрузка и результаты. Текст загрузки не является готовым кадром. `recordScreenCapture()` вызывается после сохранения PNG и связывает файл с активным runner, SHA, source=mock, viewport, проверкой готовности и SHA-256 байтов. Изменение mtime, копирование старого PNG или смена SHA не подтверждают свежесть.

Обязательны 30 кадров: исходные 26 плюс lab/outcomes на 1280×800 и 375×812. Автоматические full-page снимки и любые API-снимки в этот набор не входят. `E2E_SCREEN_REVIEW=1` оставляет кандидаты в `test-results/screen-review`; переносить их в `screens` для упаковки не нужно.

После чистого полного mock и изолированного API на одном SHA:

```text
npm run check:tools
npm run e2e:summary
npm run check:report
node scripts/review-screens.mjs --run-id <UUID mock/screens из metadata> --list
```

Просмотрите **все** перечисленные PNG: данные должны быть рассчитаны, важный текст и кнопки видны, кадр пригоден для защиты. Не утверждайте сломанный интерфейс или «Считаем решение…». Только после этого:

```text
node scripts/review-screens.mjs --run-id <тот же UUID> --approve
npm run e2e:summary
npm run e2e:pack
npm run check:report
npm run e2e:gate
```

`--approve` записывает одобрение именно просмотренных хэшей. Любая замена изображения отменяет его одобрение. Повторный прогон получает новый UUID и требует нового просмотра. Команда не заменяет фактический просмотр и не должна запускаться автоматически в тестах.

`e2e:pack` создаёт диагностический архив даже при падениях или неполном наборе снимков: в него входят только свежие manifest-bound PNG, безопасный JSON, HTML и Markdown. Неподтверждённые изображения не подставляются. `packageKind=diagnostic-not-accepted` и `acceptance.ready=false` явно отличают такой архив от принятой локальной сборки. `e2e:gate` завершается ошибкой при падении, fixme, flaky, неполном API, неверном SHA, dirty-файлах либо отсутствии всех 30 просмотренных кадров.

`check:report` сначала проверяет созданный HTML/JSON и галерею; если ZIP уже создан, дополнительно проверяет его точный allowlist и хэши. Поэтому команда работает и до, и после упаковки. Новая генерация summary удаляет прежний ZIP, чтобы старый архив не выдавался за результат нового запуска. `e2e:gate` работает только на чтение: сверяет существующий отчёт/архив с текущими SHA, runId, результатами и хэшами, не перезаписывает их и сохраняет байты валидного ZIP. Неуспешный прогон снимков блокирует gate, даже если все кадры успели сохраниться.

Сначала закончите проверки, просмотр, упаковку и gate на чистом проверяемом SHA. Затем можно отдельным коммитом добавить BUGS.md/RUN-RESULTS.md и копию уже готового ZIP в `tools/e2e/evidence/`. В документах отдельно укажите проверенный SHA и коммит отчёта; не переименовывайте SHA внутри архива и не пересоздавайте его на новом documentation-only HEAD. Gate на новом HEAD правильно потребует результаты именно нового SHA. Для воспроизведения используйте отдельный worktree точного проверенного коммита.

API-отчёт содержит только названия сценариев, итоговые статусы, число попыток, длительность и безопасную классификацию ошибки. В нём нет DOM, тел ответов, cookies, трасс, снимков или исходных сообщений исключений. Повторная попытка учитывается как flaky, а не как новый успешный сценарий.

Проверка структуры DOCX/XML не является открытием документа в Microsoft Word. Локальный API не подтверждает Docker и публичный HTTPS; эти ограничения сохраняются в отчёте.
