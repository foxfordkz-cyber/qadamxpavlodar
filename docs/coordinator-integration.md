# Кабинет координатора — подключение и проверка (участник 2)

Версия от 27.10.2026. Направление: **задание 02 «AI-карта озеленения Павлодара — свободные участки и подбор растений»**.
Главное: карта кандидатов в участки из открытых данных OSM, проверки пригодности, рейтинг, подбор растений, задания на обследование или посадку и проверка отчётов.

## Запуск

```bash
cd apps/web
npm install
npm run dev          # http://localhost:5173, тестовый источник в браузере
```

Режим данных выбирается в `VITE_DATA_SOURCE` (`.env`, см. `.env.example`) или в адресе страницы: `?source=api` или `?source=mock`.
В режиме `api` запросы идут на `/api/v1` через прокси Vite к `VITE_API_PROXY` (по умолчанию `http://localhost:3000`) с `credentials: include`.
Текущий режим всегда виден в шапке: «Тестовый источник в браузере» или «Сервер /api/v1».

Сборка: `npm run build` (сначала `tsc -b`, потом `vite build`).

## Данные OpenStreetMap

```bash
node fixtures/osm/fetch-osm.mjs      # Overpass API, центральная часть Павлодара, 3 запроса с паузами
node fixtures/osm/build-sites.mjs    # → fixtures/osm/sites.json (CandidateSite[] + EvidenceRef[])
```

- Снимок OSM от 27.10.2026: 171 контур газонов и травяных участков. После фильтра (150–25 000 м², не внутри существующих парков) осталось **114 кандидатов**.
- Лицензия ODbL, © участники OpenStreetMap. Атрибуция видна на карте постоянно.
- Подложка — OpenFreeMap (стиль `liberty`, без ключа), 3D-здания из OSM по высоте или этажности. Тайлы массово не скачиваются. Резерв без сети — собственная подписанная схема по координатам.
- Факторы `greeneryGap`, `publicUsePriority`, `maintenanceFeasibility` вычислены по OSM. Формулы — демонстрационная политика команды; у каждого фактора в `method` записан способ расчёта. `waterAvailability` = `null` для всех: открытых данных о воде нет. Координатор может внести значение с источником.
- Все проверки (`landPermission`, `utilities`, `access`, `siteSuitability`) в исходных данных `unknown`. Газон в OSM ≠ свободная земля.
- GeoJSON строго `[lng, lat]`. Экран проверяет каждую точку на попадание в район. Если lat/lng перепутаны, участок не рисуется на карте, и показывается явная ошибка.

## API: что использует экран

Конверт `{data, meta?}` / `{error:{code,message,details?,requestId}}`. Изменения передают `expectedVersion`, повторяемые операции — `Idempotency-Key`.

**Из контракта v1:**
`GET /auth/me`, `POST /auth/login`, `POST /auth/logout`, `GET /sites`, `GET /sites/:id`, `PATCH /sites/:id`, `POST /sites/rank-preview`, `GET /workers`, `GET /tasks?objectId&status&assigneeId`, `POST /tasks`, `POST /tasks/:id/assign`, `GET /reports?reviewStatus&taskId`, `POST /reports/:id/review`, `GET /dashboard`.

**Предложено в v1.1 (согласовать с участниками 1 и 3):**

| Маршрут | Зачем |
|---|---|
| `POST /sites/:id/plant-selection` → `PlantSelection` | подбор растений: функция участника 1, по форме как `Recommendation` |
| `GET /species` → `Species[]` | справочник видов (сейчас качественные оценки команды) |
| `GET /evidence?ids=a,b` → `EvidenceRef[]` | расшифровка источников в карточке |
| `GET /uploads/:id` → `{id,url,contentType,isDemo}` | показ фото отчёта |
| `GET /issues?objectId|taskId` → `Issue[]` | сообщения работников «не могу выполнить» |

**Новые поля:** у `CandidateSite` — `osmId`, `centroid`, `context` (подсказки из OSM, это не проверки) и `geometryAccuracy`; у `SiteRankItem` — `partialScore` (балл по известным факторам, сравним только внутри группы с тем же `missingFactors`).

**Тела запросов, которые ждёт экран:**
- `PATCH /sites/:id` — `{expectedVersion, checks?: {<key>: {state, comment}}, waterAvailability?: {value|null, note}}`. Комментарий обязателен для `cleared`/`blocked`, `checkedBy/checkedAt` ставит сервер. Ответ — обновлённый участок.
- `POST /tasks/:id/assign` — `{assigneeId, scheduledStart|null, expectedVersion}`.
- `POST /reports/:id/review` — `{decision: accepted|changes_requested, comment, expectedTaskVersion}`, ответ `{report, task}`.
- Ошибки валидации: `400` с `details.fields = {field: message}`. Экран подсвечивает эти поля.
- `409 version_conflict` с `details.currentVersion`. Экран предлагает загрузить свежие данные и ничего не перезаписывает.
- `503 ai_unavailable` для подбора. Экран пишет «Сервис подбора недоступен», ручное создание заданий продолжает работать.

**Обновление карты после серверных изменений:** списки участков, заданий, отчётов, сводка и открытая карточка опрашивают сервер раз в 30 секунд (только при видимой вкладке). После своих успешных изменений экран перезагружает данные сразу. Если запрос не прошёл, рядом с данными появляется «Данные могли устареть: последнее обновление ЧЧ:ММ».

## API v1.1 (предложение участникам 1 и 3)
| Маршрут | Назначение |
|---|---|
| `GET /sites/:id/context?radius=30\|50\|100\|200` → `SiteContext` | окружение; сервер считает один раз на участок и радиус, а не при каждом движении карты |
| `GET /plants` | существующие растения, в том числе после принятой посадки (`projectId`) |
| `GET /brigades` | бригады: бригадир, люди, смена, техника, навыки |
| `GET /projects`, `GET /projects/:id`, `POST /projects` | проекты озеленения |
| `PATCH /projects/:id` `{expectedVersion, items}` | правка; у согласованного проекта растёт `designVersion`, статус → `draft` |
| `POST /projects/:id/submit`, `/withdraw` | отправка на согласование и отзыв |
| `POST /projects/:id/review` `{decision, comment, expectedVersion}` | только `admin`; `approved` → 409 `checks_incomplete`, если хотя бы одна проверка участка не `cleared` |
| `POST /tasks` с `projectId`, `projectDesignVersion` | посадка только из согласованной версии (иначе 400) |
| `POST /tasks/:id/assign` `{brigadeId, minCrew, scheduledStart, expectedVersion}` | назначение бригаде; людей (`crewIds`) выбирает бригадир (участник 4) |
| `GET /plans?date=YYYY-MM-DD` → `{plan, preview}`; `POST /plans/:date/approve` | утверждение плана дня; итог и предупреждения в `summary` |

Сервер повторяет проверки клиента. Позиция в зоне исключения, за границей участка или ближе ориентира к зданию (дерево 5 м, куст 1,5 м — ориентир команды, сверить с СП РК) без письменного `resolution` → 400 `unresolved_conflict`, `details.items`. При приёмке отчёта по посадке сервер создаёт `Plant` из согласованной версии и ставит проекту `implementedAt`: плановые отметки больше не выводятся, дублей нет.
