## Переключатель в шапке

После слияния PR #9 (`787dd02`) переключатель подключён в `Shell.tsx` рядом с «Выйти», в том числе для экрана входа. Логика авторизации, выхода и маршрута `#/worker` сохранена. Импорт:

```tsx
import { LanguageSwitcher } from '../../shared/i18n/LanguageSwitcher';
```

Элемент в `gp-header__right` — одна строка:

```tsx
<LanguageSwitcher />
```

Язык можно выбрать кнопками «Рус / Қаз» или адресами `/?source=mock&lang=kk` и `/?source=api&lang=kk` (маршрут страницы остаётся после `#`). Язык сохраняется в `localStorage` под ключом `gp.language`. Смена языка вызывает повторный рендер без размонтирования страницы и потери введённой формы. URL `lang` имеет приоритет при загрузке. `VITE_ENABLE_KK=0` явно отключает казахский; без флага он доступен. Переключатель меняет общий интерфейс; внутренние тексты кабинета работника ведутся в отдельном модуле.

`t(key)` использует русский текст, если перевода нет. `tr(text)` — адаптер старых статических подписей: ищет строку в ru и берёт парный ключ kk, неизвестную строку сохраняет как есть. Переводы и для этого адаптера находятся в `kk.ts`; автоматического машинного перевода ответов API нет.

## Граница перевода и интеграционные хвосты

- Переведены исходные 691 ключ и добавлены пары для статических подписей разрешённых страниц, включая отчёт, каталог, смету, приоритеты, импорт и гайд. Месяцы и подписи общих аналитических словарей переводятся во время рендера, а не при загрузке модуля.
- После слияния `origin/codex/coordinator` (`3795f16`) переведены новые элементы `SitesPage`, `TimeMachinePanel`, `AssistantPanel`, режим презентации и действия пустых списков. Вкладки `ZONE_TABS` в карточке выводятся через `tr(label)`. Названия подсветки хранятся в URL как ключи (`hlt`, бюджет — `hlb`), переводятся при рендере; старые ссылки с русским заголовком поддерживаются.
- В `map/MapTools.tsx` по отдельному разрешению переведены только тексты поиска и рисования (`mapSearch.*`, `draw.*`), включая скрытые подписи. Обработчики, условия, расчёт площади и сохранение не менялись. Остальные `map/*` не редактировались; в `Shell.tsx` после PR #9 добавлены только импорт и элемент переключателя.
- Счётчики над списком зон и плитки обзора переводят `label` и `definition` через `tr()` при отображении. `metricPeriod()` переводит известную подпись периода OSM, сохраняя дату; неизвестный текст возвращается как есть. `dashboardMetrics` и другие исходные данные остаются на русском.
- После слияния `origin/codex/coordinator` (`dc6d56d`, включает PR #13) сохранены импорт SHP с предварительной проверкой и подтверждением, серверный экспорт PDF/XLSX и Word-записка. Новые подписи и сообщения интерфейса — `import.*` / `report.*`; значения слоёв и классов данных в запросах не переводятся. Сообщения API и пользовательские данные сохраняют исходный текст.
- `shared/analytics/assistant.ts`, `apps/server/src/tz/llm.ts`, `tz/assistantCommands.ts`, `apps/server/src/v2/*` и `apps/server/src/municipal/*` не редактировались при интеграции. В `AssistantPanel` переведены подписи, примеры вопросов и два локальных сообщения команды рисования (`assistant.drawEnabled`, `assistant.drawRestricted`); текст ответа, названия объектов, источники и причины fallback из API отображаются как получены.
- Имена объектов, пользовательский текст, названия/цитаты источников, описания видов и объяснения, пришедшие от API/расчёта, сохраняют язык исходных данных. Их отдельного казахского набора в текущем контракте нет; русская строка не маскируется пустым переводом. Названия видов не переводились без подтверждённого ботанического соответствия.
- Служебная записка создаётся на выбранном при скачивании языке «Рус / Қаз», независимо от языка интерфейса. Служебные тексты — ключи `memo.doc.*`, подписи и шаблоны расчёта — `memo.input.*` в общих `ru.ts` / `kk.ts`. `tFor` и `trFor` принимают язык явно, не меняя глобальное состояние. Числа, формулы и исходные результаты расчёта сохраняются; для Word задан язык проверки `ru-RU` / `kk-KZ`.
- Названия объектов, цитаты/описания источников и неизвестные пользовательские тексты сохраняют язык оригинала. Для вида используется `nameKk`, если он есть, иначе `nameRu`; новые ботанические переводы не выдумываются. Известные шаблоны объяснений из расчёта переводятся только при полном совпадении, параметры переносятся без пересчёта. Содержимое документа полностью редактируется в Word.

## Проверка

```bash
npm --prefix apps/web run check:i18n
npm --prefix apps/web run test
```

`check:i18n` завершается с ошибкой при пропущенном/пустом переводе, лишнем ключе или несовпадении имён и количества `{параметров}`. Русский fallback проверяется отдельным тестом. Полнота словаря не равна лингвистической вычитке или проверке каждой страницы в браузере.

### Предметная проверка 2026-10-30

База: `e6d9079840bd7a7469488031ab777a851c7f8d78` (`origin/codex/coordinator`).
Проверены все **50 записей** экспортируемого массива `species` в его фактическом порядке.
Это 50 позиций каталога, включая гибрид и внутривидовую/садовую форму, а не заявление о 50 независимых принятых биологических видах.

Итог: **24 подтверждённых названия** (22 VERIFIED_EXACT, 2 VERIFIED_SYNONYM), **26 null** (23 UNVERIFIED, 2 GENUS_ONLY, 1 CONFLICT).
Из прежних заполненных названий 19 сохранены, 2 исправлены, 3 заменены на null; ещё 3 прежних null заполнены по источникам.
Всего изменено 8 полей nameKk. Латынь, русский текст, IDs, порядок, числовые характеристики, цены и все остальные свойства сохранены.

**Научная проверка не завершена для 26 позиций с null.** Это технически безопасный результат проверки, а не утверждённый национальный справочник.
Соответствие названия виду не подтверждает пригодность посадки в Павлодаре, безопасность, цены или расчётные характеристики.

Статусы:
- **VERIFIED_EXACT** — открытый первичный документ связывает выбранное казахское имя с данным латинским видом.
- **VERIFIED_SYNONYM** — есть казахская пара в первичном документе и отдельное подтверждение научного синонима.
- **GENUS_ONLY** — установлено лишь общее/родовое имя, недостаточное для вида; null.
- **CONFLICT** — не разрешено распределение названий по таксонам; null.
- **UNVERIFIED** — в проведённом поиске нет доступного достаточного доказательства; null. Это не означает, что такого имени не существует.

У одного вида могут быть разные казахские названия. Наличие двух прямых пар для одного и того же бинома само по себе не доказывает подмену вида: в таких случаях ниже зафиксированы варианты и причина выбора. При перекрёстном отнесении одного названия к разным таксонам проверены контекст и научные синонимы. Неустранённый случай Ulmus оставлен CONFLICT.

### Ulmus pumila: отдельное решение

B1 (табл. 1, с. 70) и B11 (табл. 3, с. 132) действительно содержат «Бұтақты қарағаш» рядом с Ulmus pumila. Следовательно, прежнее название не было просто выдуманным переводом.
Однако B10 разделяет строки 74–75: «Бұтақты қарағаш» — Ulmus foliaceae Gilib / вяз перистоветвистый, а «Аласа қарағаш» — Ulmus pumila L.
В B1 род Ulmus и вид Ulmus pumila находятся в разных колонках: это видовая запись, не одно родовое имя.

В T1 у принятого U. pumila L. есть синонимы U. pinnatoramosa Dieck ex Späth и U. pumila var. arborea Litv.; это не доказывает казахское имя.
T2 относит U. foliacea Gilib. ex C.K.Schneid. к U. minor subsp. minor; написание и авторство строки B10 отличаются, поэтому её нельзя молча «исправить» и объявить синонимом.
T3 рассматривает ‘Pinnato-ramosa’ как садовое название и помечает U. pumila var. arborea как misapplied в этом контексте.
Эти данные показывают необходимость сверки конкретной таксономической концепции B10. Выбор «Аласа қарағаш» только потому, что оно привычнее, был бы необоснованным разрешением расхождения.
Результат: **CONFLICT, nameKk: null**. Ботанику нужно установить, какой таксон подразумевает строка 74 B10, и выбрать название для каталожного U. pumila L. Русское название не менялось.

### Дополнительные результаты сверки

- Дубликатов IDs и одинаковых непустых nameKk у разных латинских записей нет ни до, ни после проверки. Null не считается ботаническим названием.
- Старый glossary содержал все 50 растений, но порядок строк отличался от итогового экспортируемого массива; новая матрица следует массиву, код не переставлялся.
- «Барқытгүл» и «Агератум» в прежнем glossary уже были отмечены общими названиями, однако оставались заполненными в видовом поле. Теперь обе записи null.
- «Қазақ аршасы» не совпало с цитируемым B4: там «Казак аршасы». Взято подтверждённое «Қызыл арша» из B4/B10. «Дәріарша» B11 отвергнуто из-за отнесения близкой формы к J. sibirica в B10; механическая орфографическая замена не выполнялась.
- Для Cotoneaster lucidus проверена ранее отсутствовавшая связь с C. acutifolius (T5). Имя применимо в широком объёме вида POWO. Флоры, разделяющие эти таксоны, перечислены в T5: владелец каталога должен отдельно согласовать используемую таксономическую концепцию, если нужен более узкий таксон.
- Для Prunus padus научный синоним Padus avium доказан отдельно (T4). Для Hylotelephium spectabile и Dasiphora fruticosa научные связи не дали казахского названия и не стали основанием заполнить поле.
- Populus alba var. pyramidalis — внутривидовая/садовая форма; Petunia × hybrida — гибридная запись. Русские «Лилейник», «Хоста», «Пион травянистый» и названия однолетников менее точны, чем латынь. Не исправлялись вне согласованного scope.

### Обновление названий в существующей API-базе

`tz/seed.ts` берёт `web.species` из общего каталога и сохраняет весь JSON (включая nameKk)
в `tz_species.data`; повторный INSERT имеет `ON CONFLICT(id) DO NOTHING`.
`seedMunicipal` дополнительно сохраняет `municipal_state['species']` только при отсутствии ключа.
`municipal.catalog()` объединяет данные с приоритетом справа:
`web.species → tz_species → municipal_state['species'] → municipal_features['catalog']`.
И `/api/v1/species`, и муниципальный каталог используют это объединение. Поэтому даже обновление
одного `tz_species` может быть скрыто прежним значением в municipal_state или импортом.
`v2_documents(kind='catalog')` хранит отдельное представление с displayName/nameRu и botanicalName;
его нельзя слепо заменять полным frontend Species DTO.

После merge новый чистый seed получит проверенные названия. Для существующей БД нужен отдельный
согласованный patch, если эффективный API-каталог всё ещё старый. Полный reseed не нужен.

Patch должен сравнить ID, текущий nameKk и версию с известной исходной записью; изменить только
8 проверенных различий nameKk в слоях, которые всё ещё содержат исходный каталог. Пользовательские
правки/импортированные overrides пропускать с отчётом, а не перезаписывать. Сохранить ID, латынь,
русское имя, порядок и характеристики; не пересчитывать сохранённые прогнозы Outcomes.
Затем проверить эффективный GET /species, повторное применение без изменений и restart.
