# Лаборатория решений: контракт и демонстрация

Маршрут `#/lab`, read-only `POST /api/v1/decision-lab`. Продолжение существующего PR #28, одна реализация для mock/API и проверки фиксированного снимка в браузере. Схема входа: budgetKzt > 0, waterLimitM3 >= 0 либо null, watering=regular/rare/none, необязательный goal=balanced/schools/deficit/social (по умолчанию balanced). Неизвестные поля отклоняются.

## Расчёт

- Базовый анализ `optimal`, обычный полив, `careYears: 3`. Материал, подготовка, работы вместе с доставкой, уход и резерв проверяются через существующий outcomes-контракт. Неполная цена исключает зону из отбора. Цены не распределяются произвольно между деревьями и цветами.
- Первая стратегия ранжирует ожидаемые деревья за 3 года на тенге полной сметы, вторая — воду на т CO₂/год на 20-м году, третья — существующий индекс с весами social=.5, density=.25, deficit=.25. Это детерминированные жадные предложения, не доказанный глобальный оптимум. Равенства разрешаются индексом и siteId; совпавшие планы явно помечаются.
- Ожидаемые деревья: сумма `quantity*y3/100` только по tier=tree. Средняя приживаемость: expectedTrees/treeCount*100. Нулевой знаменатель — null. Сумма крон не является уникальной площадью тени; охлаждение города не суммируется.
- Вода: число визитов из строк «Полив» × (число деревьев × норма дерева + число кустов × норма куста) / 1000. Цветы и влагозарядковый полив исключены. Null нормы сохраняется как неизвестность. При заданном лимите неизвестный расход не считается допустимым.
- Доступность воды при уменьшении на r%: limit*(1-r/100). Дефицит: max(0,demand-available). Это не модель смертности. Доля покрытия ограничена 100%; при нулевой потребности неизвестна. Если лимит не задан, пользователь явно вводит его или принимает максимум потребности трёх планов.

## Общественная цель и источники

Используется существующий `siteContext` с геометрическим расстоянием до контуров OSM в пределах 400 м. Только явные теги назначения из адаптера дают school/kindergarten/social. Имена и свободные строки `socialWithin400m` не доказывают наличие школы. Одинаковые id дедуплицируются, итоговое число социальных объектов — объединение по id всех зон. Полнота OSM не гарантируется, отсутствие записи не означает отсутствие объекта.

Цель schools/social сначала рассматривает подтверждённые подходящие зоны одинаково во всех стратегиях; затем остальные. Deficit сначала рассматривает известную меньшую долю зелени. Базовый индекс city.ts сохраняет своё допущение для отсутствующей доли; оно отдельно объясняется на экране. Сведения о жителях не выдумываются, официальный Tree Equity Score не заявляется.

## Фиксированный план и явные изменения

Ответ содержит исходные зоны, схемы, каталог, ставки, source/capturedAt/ratesVersion. Чистый `evaluateDecisionPlans` использует этот снимок, пересчитывая существующие survivalForecast/costEstimate/careCalendar/ecoEffect на **той же схеме**, не вызывая buildScheme. Ни зоны, ни виды, ни количества от переключения полива не меняются. Текущие ставки и изменение DataProvider revision не обновляют снимок автоматически; есть явное обновление. Смена входных ограничений строит новый базовый план с задержкой 300 мс и отменой устаревшего запроса.

Редкий полив — существующий scale=.5 с округлением визитов. Процент изменения воды вычисляется, не задаётся константой. Стоимость ухода в нынешней смете не уменьшается пропорционально воде, резерв замены может увеличиться; перерасход виден. Устойчивость сравнивается по потере приживаемости, разница <1 п.п. — правило отображения, не статистическая значимость.

«Перестроить» делает новый серверный/mock расчёт под изменённый общий водный лимит и показывает добавленные/исключённые зоны, стоимость, воду и ожидаемые деревья рядом с прежними. Изменение бюджета/цели также перестраивает план.

## Климат и замены

Сухое лето, суровая зима и задержки ухода — диагностические карточки. Текущая модель не вычисляет их количественное воздействие, поэтому коэффициенты потерь не вводились. Для деревьев показаны droughtTolerance/frostHardiness из каталога, для ухода — число операций/выездов. Альтернативы берутся только из подходящих ranked species (score>=50, не excludedBy), того же яруса, с более высокой соответствующей устойчивостью и без дублирования уже выбранного вида.

Полная стоимость замены пересчитывается существующими функциями на прежних количествах. Применение — только отдельной кнопкой, лишь к выбранной зоне выбранного плана. Неизвестная стоимость не разрешает применение. Перерасход бюджета/воды отображается. Это вариант в памяти текущей страницы, не серверное сохранение; после обновления страницы строится новый план.

## Границы и совместимость

plan.ts, city.ts, модель приживаемости, движок карты, worker, v2 и municipal не менялись. Read-only роли coordinator/admin/viewer; worker/foreman запрещены серверным reader. Не добавлены записи/миграции/права. OpenAPI строится из router. Кэш включает вход, сайты, каталог, ставки и версию. API-ошибки остаются API-ошибками.

Карта использует существующий `hl` и лимит 30 зон: для больших планов виден выбор нумерованной группы. Dropdown «Ещё / Тағы» выровнен по правому краю, чтобы новые разделы не воспроизводили E2E-07.

RU/KK имеют полный набор ключей; казахский текст черновой и требует вычитки Бекзатом. Прогноз и демо-расценки не объявляются полевыми фактами. Произвольный текстовый разбор запроса не добавлен: бюджет/вода/цель заданы явными полями. Климатическая модель, постоянное серверное сохранение городских планов и подтверждение пригодности посадки на местности не заявляются.

## Проверка и показ

Node 24, зависимости apps/web, apps/server, tools/e2e и Chromium. Из tools/e2e: `node scripts/isolated.mjs mock` и `node scripts/isolated.mjs api`. Каждый запуск поднимает отдельный Vite; API создаёт отдельную SQLite и выполняет TZ seed, пароль существует только в памяти/окружении дочерних процессов. API trace/video/screenshots отключены. Mock-снимки записываются для просмотра, не заменяют эталоны автоматически.

60 секунд: 50 млн + лимит + школы → три плана и сметы → карта выбранной группы → −30% воды и дефицит прежнего плана → «Перестроить» и изменившиеся зоны → оговорки о прогнозе/демо-данных. До публикации в coordinator нужны ревью и результаты полного mock/API на одном SHA; Docker/HTTPS требуют отдельной согласованной среды.
