# Перенос в репозиторий организаторов с сохранением истории

Этот документ — план переноса, **не отчёт о выполненной публикации**. В репозиторий организаторов при подготовке этой инструкции ничего не отправлялось.

## Что проверено 1 ноября 2026 года

- Исходный репозиторий: [foxfordkz-cyber/qadamxpavlodar](https://github.com/foxfordkz-cyber/qadamxpavlodar), основная ветка `codex/coordinator`.
- Адрес из переписки: [AIFESTHackathon2026/team-qadamx](https://github.com/AIFESTHackathon2026/team-qadamx).
- Чтение через `git ls-remote` и отдельный fetch доступно. У организатора есть `main`, коммит `d179a24962e525130c65f7648f844ee4d8423533` (`Initial commit`). В его дереве только `README.md` с заголовком `team-qadamx`.
- Это подтверждает доступ на чтение. Право push, branch protection и разрешение Actions нужно проверить отдельно. GitHub-коннектор возвратил 404; это не означает, что репозитория нет: чтение теми же Git-командами с локальной Git-авторизацией прошло.
- Организатор в предоставленной капитаном переписке просит загрузить работу в репозиторий организации. Ссылка на исходную разработку в README сама по себе этот перенос не выполняет.

## Что сохраняется

Можно скопировать все опубликованные ветки и теги вместе с достижимой историей. У прежних коммитов сохраняются SHA, авторы, даты и граф слияний. Для объединения исходной основной ветки с начальным коммитом организатора создаётся новый merge-коммит, прежняя история остаётся его предками. Перенос веток не означает вливание всех экспериментальных веток в финальный код. [Копирование репозитория, GitHub Docs](https://docs.github.com/en/repositories/creating-and-managing-repositories/duplicating-a-repository).

Обычный Git-перенос не переносит PR, обсуждения, Issues, результаты Actions, настройки доступа, секреты и объекты публикаций сайта. Исторические ссылки на исходные PR сохраняются. При необходимости в README можно дать ссылку на исходную историю разработки. Полный Transfer repository — другая операция со сменой владельца и требованиями к правам; для уже созданного репозитория команды её не следует подменять обычной загрузкой. [Перенос владельца, GitHub Docs](https://docs.github.com/en/repositories/creating-and-managing-repositories/transferring-a-repository).

Локальные незакоммиченные файлы, `.env`, базы, uploads и приватные окружения в такой перенос не входят. Не добавляйте их ради «полной копии». Git LFS, если он используется хотя бы в одной переносимой ветке, требует отдельной передачи объектов. [GitHub о переносе LFS](https://docs.github.com/en/repositories/creating-and-managing-repositories/duplicating-a-repository#mirroring-a-repository-that-contains-git-large-file-storage-objects).

## Порядок для капитана

1. Закончить согласованные слияния в исходном `codex/coordinator`. Зафиксировать точный SHA кандидата, отчётов и публичных frontend/backend. Не вливать Draft только ради переноса.
2. Все участники отправляют законченные коммиты в исходный репозиторий обычным push. На время финального копирования согласовать короткую паузу: перенос не синхронизируется автоматически с последующими коммитами.
3. В **новом отдельном каталоге** сделать bare-клон исходного репозитория. Он получает ветки сервера как локальные `refs/heads/*`; простой `git push --all` из обычного worktree не включает автоматически все remote-tracking ветки.
4. Сохранить список `refs/heads/*` и `refs/tags/*` с SHA, резервный Git bundle и список ссылок на важные PR. Перед копированием всех веток проверить, что старые ветки тоже не содержат секретов. При обнаружении секрета не публиковать его, заменить/отозвать у провайдера и отдельно согласовать очистку; не обходить запрет на переписывание истории молча.
5. Перечитать ссылки организатора: его `main` мог измениться. Обычным push перенести только ветки и теги без перезаписи существующих несовместимых ссылок. Сначала `--dry-run`, затем реальная отправка после просмотра плана. Ошибка доступа, защита ветки или конфликт SHA — повод остановиться, а не добавлять force.
6. Отдельно создать в целевом репозитории ветку сдачи от его `main` и объединить **только проверенный `codex/coordinator`**. Для двух независимых корней допустим обычный merge с `--allow-unrelated-histories`; вручную сохранить README проекта, заголовок команды и любые инструкции организатора. Не использовать squash: он не делает всю исходную историю предками `main`. [Git merge](https://git-scm.com/docs/git-merge).
7. Открыть PR в `main` репозитория организатора. Проверить дерево и включённые SHA, затем капитан или организатор выполняет обычное слияние. Ветка по умолчанию должна показывать проект, а не оставаться на первоначальном заголовке.
8. Настроить CI для целевой основной ветки и повторить проверку уже там. Сейчас `.github/workflows/quality.yml` запускается для `codex/coordinator`; если сдаётся `main`, нужно отдельно добавить её в фильтры push/PR, сохранив существующий вариант. Зелёные Actions исходного репозитория не называются запусками нового.
9. Сравнить SHA каждой скопированной ветки/тега, проверить наличие обеих README, скриншотов, презентаций, запуск и доступ судей. Выдать итог: URL, SHA `main`, SHA исходного кандидата, результат CI и ограничения. Старый репозиторий оставить доступным для истории PR.

## Команды для этапа копирования веток

Ниже пример для PowerShell. Это **будущие команды с записью в целевой репозиторий**, не выполненные при подготовке документа. Выполнять после согласования итоговой версии и проверки прав, в новом каталоге. После ошибки не продолжать следующий шаг. Путь для клона выбрать свободный, не заменять существующий worktree.

```powershell
git clone --bare https://github.com/foxfordkz-cyber/qadamxpavlodar.git C:\gp-submission-copy.git
```

После успешного клонирования:

```powershell
Set-Location -LiteralPath C:\gp-submission-copy.git
git fsck --full
git for-each-ref --format='%(objectname) %(refname)' refs/heads refs/tags
git bundle create C:\gp-submission-history.bundle --all
git bundle verify C:\gp-submission-history.bundle
git remote add organizer https://github.com/AIFESTHackathon2026/team-qadamx.git
git ls-remote --heads --tags organizer
git push --dry-run --atomic organizer 'refs/heads/*:refs/heads/*' 'refs/tags/*:refs/tags/*'
```

Проверить вывод: никакая существующая ветка организатора не удаляется или не заменяется несовместимой историей. Если план принят и все команды успешны, выполнить обычный push тех же refs:

```powershell
git push --atomic organizer 'refs/heads/*:refs/heads/*' 'refs/tags/*:refs/tags/*'
git ls-remote --heads --tags organizer
```

Ветка организатора `main` останется на месте, если в источнике нет одноимённой ветки. Передача `codex/coordinator` сама по себе не меняет страницу `main`; объединение из пункта 6 обязательно. При конфликте одноимённых веток требуется отдельное решение, а не перезапись. Atomic push не переносит платформенные метаданные и не заменяет последующую сверку SHA.

Не использовать `git push --mirror`: он может принудительно обновлять и удалять ссылки получателя. Здесь нужны обычные, явно выбранные ветки и теги. [Семантика push, Git](https://git-scm.com/docs/git-push).

## Что не меняется от копирования Git

Cloudflare, Render и Supabase не переезжают автоматически. Текущие публичные адреса продолжают относиться к своим зафиксированным публикациям. Не переключайте автодеплой на новый репозиторий без отдельной проверки: загрузка истории для жюри не требует менять сервер, пароли или базу. Идентификаторы опубликованных сборок сохраняются в [передаче публикаций](cloud-publication-handoff-2026-11-01.md).
