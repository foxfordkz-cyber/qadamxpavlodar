# «Прогноз и факт»: рабочий экран и источник mock

Ветка `codex/outcomes-workflow` продолжает #18 и #21. Обе зависимости включены обычным
merge. Ветка `codex/outcomes-ui` и PR #21 другого участника не перезаписываются.

Новый маршрут: `#/outcomes`, пункт «Прогноз и факт» в меню специалиста, администратора
и просмотра. Во вкладке «Смета» зоны есть переход с сохранением выбранной зоны.
Компактный `OutcomesPanel` из #21 подключён к тому же источнику; карточки стоимости
`CostCard` переиспользуются подробным экраном. Его исходные тесты и тестовый стенд сохранены.
Вход, выход, маршрутизация работника, карта и серверные модули не изменяются.

## Что работает

- Три варианта через существующий `analyzeZone`, со справочником видов и ставок из
  выбранного источника. Уход — три года. «Только деревья» исключает другие ярусы **до**
  расчёта. Это отдельное сравнение, не изменение текущей сметы карточки зоны.
- Полнота сметы, цена ожидаемо сохранившегося дерева и выбор минимального варианта —
  функции #18. Неполные расходы и смешанная посадка не дают победившую «нулевую» цену.
- Сохранение прогноза в mock: снимок пересчитывается на стороне mock, проверяются
  версии зоны/ставок, право специалиста и ключ повтора. Снимок и запись повтора
  сохраняются одним значением localStorage. Ошибка хранилища возвращает явный отказ;
  состояние в памяти не заменяется и успешное сохранение не показывается.
- Сохранённый прогноз можно выбрать и посмотреть после перезагрузки. Показаны исходные
  статьи затрат, виды, y1/y2/y3, диапазон y1 и источники ставок. Текущие изменения
  справочников его не переписывают. Это не архив на сервере и не резервная копия браузера.
- Выбор партии и конкретного осмотра, исходный прогноз партии, подтверждённая дата посадки,
  охват осмотром и установленным состоянием, живые/погибшие/неизвестные/неосмотренные.
- Отклонение от прогноза появляется только при полном установленном состоянии и точной
  календарной годовщине по контракту. Без даты, снимка или подходящего осмотра показывается
  причина. Прогноз и цена могут быть демонстрационными отдельно от настоящих наблюдений.
- Отмена публикации устаревших ответов при смене зоны; ошибка обновления скрывает прежние
  значения. RU/KK, русский fallback названий видов, раскладка 375 px.

Новых зависимостей нет. Исходные формулы и модель не менялись. Нет заявлений о полевой
точности, причинном влиянии ухода или автоматическом переобучении.

## Граница API — для Бекзата

При проверке GitHub 30.10.2026 API партий/осмотров не был опубликован. Поэтому
production endpoints не придуманы, а `?source=api` **не обращается к mock-хранилищу**:
расчётные карточки используют настоящие `sites/species/rates`, история показывает
«Хранение партий и осмотров на сервере ещё не подключено». Сохранение не предлагается.

`shared/api/outcomesClient.ts` — UI-порт, не второй серверный контракт:

```ts
interface OutcomesClient {
  available: boolean;
  list(siteId: string): Promise<OutcomeSiteData>;
  saveForecast(siteId: string, input: SaveOutcomeForecast, idempotencyKey: string): Promise<SavedOutcomeForecast>;
}
```

`OutcomeSiteData` объединяет DTO #18: `siteId`, серверную дату `asOf`, `cohorts`,
`inspections`, `registry` и сохранённые снимки `forecasts: {id, snapshot}[]`.
`SaveOutcomeForecast` содержит параметры плана и ожидаемые версии зоны/ставок.
`SavedOutcomeForecast` — `{id, snapshot}`. Формулы и поля партии не дублируются.

Когда маршруты согласованы, передать адаптер вторым аргументом
`createApi(observedTransport, outcomesBackend)` в DataProvider. Реальный адаптер
должен использовать существующую авторизацию/CSRF и связывать эти операции с
опубликованными серверными методами. Фиктивные mock-маршруты `/outcomes/:siteId`
и `/outcomes/:siteId/forecasts` **не являются предложением production URL**.

Обязанности сервера сохраняются: права и доступ к зоне, подтверждённые растения,
принятые источники осмотров, неизменяемый снимок, точные версии и идемпотентность.
Клиентская проверка состава партии не заменяет серверную. Отбор реестра через координаты
недопустим. Дата `asOf` приходит с сервера в календаре UTC+5.

Не подключены до backend: создание настоящей партии, ввод/сохранение полевого осмотра,
автоматическое преобразование отчёта работника в наблюдение и сохранение прогноза в БД.
Снимок, сохранённый сейчас, не присваивается задним числом уже высаженной партии.

## Демонстрационные данные

Открыть `?source=mock&lang=ru#/outcomes?site=site-osm-1569993037`.
Зона — OSM «Газон у улица Толстого». Сведения о посадке и осмотрах **вымышлены**.
Видна постоянная пометка. Прогноз для вымышленной посадки 2025 года рассчитан нынешней
моделью: это пример интерфейса, не историческая валидация.

История добавляется лениво при первом чтении outcomes и не заменяет существующий mock.
Растения добавляются в общий `MockDb.plants`; связи идут через новые явно демонстрационные
выполненные проекты. Отдельного реестра растений нет. Геопозиция в демонстрации условная,
в центре зоны; она не служит основанием принадлежности партии.

Три партии:

1. Полный осмотр: весь состав экономного плана, все состояния установлены. Контрольная
   годовщина 15.10.2026 и дополнительный осмотр 01.10.2026. Для второго сравнение запрещено.
2. Частичный осмотр: записи для половины партии, первая запись с неизвестным состоянием.
   Поэтому охват осмотром отличается от доли растений с установленным состоянием.
3. Дата не подтверждена: три зарегистрированных дерева, все живы; дата посадки и исходный
   прогноз отсутствуют. Ноль погибших показан как ноль, но отклонение не вычисляется.

Значения плана не подгоняются к цене или «хорошему» исходу. В других зонах без истории
показывается пустое состояние и ссылка на демонстрационный пример. Права mock совпадают
с текущей ролью: просмотр/администратор читают, прогноз сохраняет специалист.

## Воспроизведение проверок

```powershell
cd apps/web
npm ci
npx tsc -b
npm run build
npm test
npm run check:i18n
npm run check:zones
npm run check:survival
npm run check:care
```

Для браузера установить существующий Playwright из `tools/e2e` и запустить Vite в одном
терминале. В другом терминале из `apps/web`:

```powershell
$env:OUTCOMES_UI_BASE = 'http://127.0.0.1:5181'
node scripts/check-outcomes-workflow.mjs
node scripts/check-outcomes-ui.mjs
```

Первый скрипт проверяет настоящее приложение в mock; второй — исходный стенд #21.
Снимки и JSON результатов пишутся в игнорируемую папку `dist-tests`.
Для API экспортирована `runOutcomeWorkflow('api', password)`; пароль передавать только
из окружения/изолированного тестового процесса. Скрипт не создаёт сервер и не хранит пароль.
API-проверка подтверждает чтение настоящих справочников и отсутствие подмены истории,
а не работу ещё не опубликованного API осмотров.

Серверные и worker-тесты запускать штатными `npm test`. `tools/e2e` запускается без изменений.

## Сценарии для Айданы

- RU/KK × 375/1280: сравнение, сохранение, reload и выбор снимка.
- Полная/частичная/без даты партия; осмотр на годовщину, раньше неё и отсутствие выбора.
- Смешанная посадка и отсутствующая расценка не становятся самыми дешёвыми.
- Смена зоны или осмотра не оставляет показатели предыдущего выбора.
- Ошибка источника и повтор; quota/запрет localStorage не показывают успех сохранения.
- Роль просмотра не сохраняет; повтор с тем же ключом даёт один снимок; изменение цены
  не меняет старый снимок; сохранение со старой версией справочника отклоняется.
- API: без вымышленных осмотров; после подключения Бекзата — повторный полный цикл
  сохранения/перезагрузки/проверки источников и прав на настоящем сервере.

## Короткий показ для Танирберді

Сравнить варианты на три года → сохранить прогноз → открыть явно демонстрационную
историю → полный осмотр и отклонение → частичный осмотр и недостающие сведения →
переключить язык. Отдельно проговорить, что историческая партия демонстрационная,
а подключение серверного хранилища является самостоятельным этапом.

Это описание поведения функции; единый сценарий защиты остаётся в `docs/defense/`.
