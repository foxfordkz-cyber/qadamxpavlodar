ЗАДАЧИ

AI-01 — Ассистент: LLM, RAG и вызов функций, P0.
Новая папка apps/server/src/ai/. Адаптер модели: провайдер, модель и ключ берутся только из env на сервере (LLM_PROVIDER, LLM_MODEL, LLM_API_KEY); провайдер — тот, на который у команды есть ключ. Инструменты — существующие функции: analyzeZone, варианты зоны, detectProblems, priorities, roadmap, замена вида, поиск по каталогу, справочник расценок. RAG: каталог растений, справочник коэффициентов с источниками и docs/methodology.md. Для такого объёма хватит поиска BM25 или по ключевым словам в памяти, отдельная векторная база не нужна. Ответ — AssistantReply {text, zones, method: 'model', intent, sources, toolCalls, data}. Каждая цифра в ответе берётся из результата инструмента; ссылки на зоны — только id из результатов; если данных не хватает, ассистент прямо говорит об этом (3.10.2). Таймаут 15 секунд. Нет ключа, ошибка или таймаут — работает текущий answer() на правилах с method: 'rules'. Проверь четыре запроса из ТЗ 3.10.1 и пять своих, включая «что можно озеленить на 5 млн» и «замени клён на липу». В браузерном тестовом источнике остаётся ассистент на правилах: ключа в браузере быть не должно. Запасной вариант, если сценарий в api не успеет: в режиме mock отправлять на сервер только /assistant (флаг VITE_ASSISTANT_SOURCE=api); договорись с участниками 1 и 2.

AI-02 — Приживаемость: правила, ML и метрика, P0.
Папка ml/: генератор синтетической выборки на основе экспертных правил из plan.ts, с шумом и факторами риска (засоление, кислотность, полив, близость дороги, освещённость, возраст саженца); разбиение на train и test; логистическая регрессия или градиентный бустинг (scikit-learn); ROC-AUC на тестовой выборке (цель ТЗ — не ниже 0,75); калибровка. На сайте Python не запускаем: экспортируй коэффициенты в JSON, а survivalForecast считает по ним в TypeScript, если файл есть. Факторы риска в процентных пунктах и диапазон остаются. В docs/methodology.md честно опиши: выборка синтетическая, метрика показывает согласованность модели с правилами, а не реальную точность; что нужно для калибровки на данных Павлодара.

AI-03 — Предложение графика ухода, P1.
Функция careSchedule(zone, plan, {months, crewVisitsPerMonth, budgetKzt}) возвращает черновики заданий по календарю ухода: действие (water, weed, inspect, plant), срок, минуты, литры воды; бригада не назначена. Учитывает проблемные факторы зоны, бюджет на уход и допустимую частоту выездов бригады (3.6.3), объединяет операции в один выезд и предупреждает, если план не помещается. Маршрут POST /zones/:id/care-schedule подключает участник 2, кнопку делает участник 1. Второе — адаптер планирования дня для POST /plans/preview (V2Adapters): распределить задания по бригадам с учётом смены, capacityMinutes, навыков и воды; то, что не поместилось, — в unassignedTasks с объяснением; method: 'rules'.

AI-04 — Приоритеты и дорожная карта, P1.
roadmap сейчас жадный. Сделай отбор зон под бюджет как задачу о рюкзаке (динамика по бюджету с шагом 100 000 ₸) и объясняй, почему зона вошла или не вошла. Кэшируй analyzeZone внутри priorities. Режим «лучшее, что можно сделать на сумму N» (3.9) — для ассистента и страницы «Приоритеты».

AI-05 — Пробелы в расчётах, P1.
В analyzeZone поле before.canopyM2 всегда 0 — считай существующую крону по слою зелени и osmTrees150m, иначе «до/после» неверно. Расценка care.water.flower есть в rates.ts, но календарь ухода её не использует — подключи для цветников. Пыль (eff.dust.tree) и зелень на жителя (eff.population): найди коэффициенты с источником или оставь «нет данных» с объяснением; население — из открытых данных с пометкой «оценка». Проблема «деградация насаждений» (пятый тип в 3.2.1): правило по GreenObject.condition, которое включится, когда участник 2 импортирует карту насаждений организатора.

AI-06 — Тесты расчётов, P1.
node --test через tsx для shared/analytics: оценки в диапазоне 0–100, проценты 0–100, сумма статей сметы равна итогу, монотонность (полив повышает прогноз, засоление понижает), эталон для зоны «Газон у улица Толстого» из docs/example-report.md, все намерения ассистента. Скрипт test:analytics в apps/web/package.json — договорись с участником 1.

AI-07 — Методика для жюри, P1.
docs/methodology.md на 1–2 страницы: формулы подбора, сметы, приживаемости, эффекта и приоритета; таблица коэффициентов с источниками; допущения и ограничения; что синтетика; как работает ассистент и почему он не выдумывает.

НЕ ДЕЛАЙ
- не пиши «AI уверен на 97%» и любые проценты без метрики;
- не выдавай метрику на синтетике за реальную точность;
- не давай LLM писать числа, которых нет в результатах инструментов;
- не клади ключ в код, git или браузер;
- не меняй форму ответа /zones/:id/analysis без согласования с участниками 1 и 2;
- AI ничего не меняет сам: статусы заданий, проверки и согласования он только предлагает, решает человек.

5. КОНТРАКТ
Маршруты /api/v1 и их типы — в apps/web/src/shared/api/types.ts и api.ts, хранитель — участник 2. Типы результатов расчётов — в shared/analytics, хранитель — участник 3. Тестовый источник и настоящий сервер отдают одинаковые ответы в обёртке {data, meta} или {error}. Перед изменением контракта — сообщение в чат команды, потом PR с ревью затронутого участника.

Новые точки контракта на эти дни:
- POST /api/v1/zones с телом {name?, geometry: GeoJSON Polygon} возвращает CandidateSite с id вида site-user-N: площадь, центр, окружение, почва. Нужна для нарисованной зоны. Делает участник 2 (сначала в mock, потом на сервере), использует участник 1.
- POST /api/v1/assistant: AssistantReply получает поля method ('model' или 'rules'), sources ([{id, label, url?}]) и toolCalls ([{name, args}]). Логика — участник 3, маршрут на сервере — участник 2, показ — участник 1.
- GET /api/v1/assistant/history — хранит участник 2, показывает участник 1.
- POST /api/v1/zones/:id/care-schedule с телом {months, crewVisitsPerMonth?, budgetKzt?} возвращает {tasks: черновики заданий, warnings, method}. Логика — участник 3, маршрут и сохранение заданий — участник 2, кнопка в карточке зоны — участник 1, задания в кабинете бригады — участник 4.

6. ПРАВИЛА ДЛЯ КОДА И ДАННЫХ
- Интерфейс на русском, все строки — в shared/i18n/ru.ts. ID — строки. Даты — ISO 8601 в UTC, на экране UTC+5. В GeoJSON порядок координат строго [lng, lat].
- Неизвестное значение — null и запись в missingData, а не 0. Ничего не выдумывать: нет данных — так и пишем «нет данных» (п. 5.5 ТЗ).
- Все результаты помечены как оценка (п. 5.2). У каждого коэффициента есть источник (п. 5.3). Синтетические данные помечены как синтетика.
- Ключи и пароли — только в .env на сервере. Никогда в браузерном коде и никогда в git.
- Режим mock должен работать всегда: это запасной вариант на защите. Не ломай его.
- Никакого force push в общие ветки. Не перезаписывай чужие незакоммиченные изменения. Не копируй папки из одной ветки в другую — только git merge.
