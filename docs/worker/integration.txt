Это модуль для общего приложения. Сервер, auth, shared UI и packages/contracts принадлежат другим участникам.

ФАЙЛЫ И ПОДКЛЮЧЕНИЕ
Основной код: apps/web/src/features/worker/.
worker.mjs регистрирует <green-worker>. Его configure принимает gateway, user, scope, date, demo, locale, embedded.
embedded:true скрывает демонстрационную боковую панель и верхнюю шапку, чтобы не дублировать общую оболочку.
Общие цвета передаются CSS-переменными --gp-ink, --gp-muted, --gp-green, --gp-paper, --gp-line и другими --gp-*.
React-обёртка: WorkerCabinet.tsx. Маршрут #/worker: WorkerPage.tsx, его показывает Shell для ролей бригадира и работника. В режиме mock кабинет берёт данные из учебного источника tools/worker-demo (demo-gateway.mjs, загружается лениво), в режиме api — из маршрутов V2 через createV2Transport. Зависимости общей сборки не изменены, пакет демо расположен отдельно в tools/worker-demo/package.json.
Пример подключения с настоящим транспортом: docs/worker/integration-example.mjs.
Настоящий вход и выход выполняет общий сервер. worker-logout сообщает оболочке, что нужно завершить общую сессию.
После смены пользователя configure вызывается заново. organizationId необязателен; по умолчанию pavlodar-demo. scope различает demo/production, черновики дополнительно разделены userId.

ОДИН СЛОЙ ДАННЫХ
contract-v2.mjs содержит createContractGateway и createV2Transport.
createV2Transport отправляет fetch в /api/v1 с same-origin cookie, принимает {data,meta?}, преобразует {error} в исключение с status/code/requestId.
Idempotency-Key передаётся заголовком. Изменяемые сущности передают expectedVersion.
POST/PUT/PATCH получают X-CSRF-Token из login/me. При 403 CSRF_REQUIRED transport обновляет /auth/me и повторяет запрос ровно один раз с прежним телом и ключом; прочие 403 не повторяются.
Локальный tools/worker-demo/demo/v2-source.mjs реализует тестовый транспорт на этой же границе. Это не реализация сервера участника 3.
TaskStatus строго draft/assigned/in_progress/submitted/verified. reviewStatus строго pending/accepted/changes_requested.
UI section current/submitted/confirmed — группа списка, не новый серверный статус.
После возврата submitted -> assigned, нужно повторно начать исправление. Подтверждённая работа не начинается заново.

ФАКТИЧЕСКИЙ КОНТРАКТ СЕРВЕРА
1. Сессия: {data:{user,csrfToken}}; organizationId отсутствует. Shell понимает и эту форму, и прямой Me из mock.
2. Все списки: {data,meta:{limit,offset,total}}, максимум limit=200. Адаптер догружает страницы и не передаёт неподдерживаемый tasks?date.
3. Состав бригады берётся из crews.members; бригадир также является участником. API assign-workers принимает только {expectedVersion,workerIds}; расписание и ответственный назначаются координатором.
4. uploads: multipart file + taskId, в ответе contentUrl. GET /uploads/:id возвращает image/webp по cookie сессии. Это источник img, а не JSON. Максимальный файл — 5 MiB.
5. Вклад: {expectedVersion,expectedDraftVersion,note,photoIds,location,confirmedObservation}. expectedVersion — задача; expectedDraftVersion — черновик, включая 0. Не более 10 фото. Ответ — черновик с taskId/version, без обязательного id.
6. Итог: {expectedVersion,note,photoIds,actualWorkerIds,actualPlantingItems,location,confirmedObservation}; групповой итог также expectedDraftVersion. actualWorkerIds содержит хотя бы одного участника, фото не более 20. Ответ — {data:{report,task}}.
7. Проблема: {expectedVersion,text,confirmedObservation}; text составляется из причины и заметки. Поля фото этот маршрут не принимает.
8. Подтверждённое наблюдение: {category,extractedFacts,proposedAction:null|action,evidenceIds,missingData,confirmed:true}. Неподтверждённый анализ не отправляется. Интерпретация заметки принимает {taskId,text} и Idempotency-Key.
9. revisionOf, deviceTime, foremanChecked и contributorIds не отправляются в теле отчёта. Сервер фиксирует происхождение и связь исправления самостоятельно; capturedAt допускается внутри location.
10. GET /designs/:id возвращает {id,revisions}; выбирается только approvedDesignId + approvedDesignVersion со статусом approved. При отсутствии этой ревизии начало/отчёт посадки блокируются. Работник не вызывает запрещённый plant-catalog; бригадир видит только позиции выбранной ревизии.
11. Фактическая посадка содержит plantingItemId,catalogItemId,quantity>0,geometry Point/MultiPoint и необязательный note. Число фактических точек равно quantity. Вклад работника не содержит фактические количества.

ОТЧЁТЫ И ВЕРСИИ
Одиночная задача: назначенный исполнитель загружает фото и отправляет итог.
Совместная задача: участник загружает собственное фото и заметку, затем получает «Материалы добавлены». Статус задачи остаётся in_progress.
Бригадир проверяет общий черновик, отмечает фактических участников и вручную задаёт итоговые количества. Количества материалов не суммируются автоматически, чтобы два человека не удвоили один объект.
Итог получает pending, задача submitted. Только coordinator принимает итог. Предварительная проверка бригадира не заменяет приёмку.
Неполные количества можно зафиксировать в отчёте, но приёмка полной посадки должна отказать и потребовать исправления/согласования.
Одинаковый Idempotency-Key с тем же содержимым возвращает прежний результат до проверки уже изменившегося статуса.
Ответ потерян после сохранения: клиент сохраняет frozen payload и повторяет его без изменений.
409: после явного «Обновить версию для исправления» клиент создаёт новый ключ, сохраняет текст и повторно проверяет актуальные данные.

ГРАНИЦА БЕЗОПАСНОСТИ
Тестовый источник проверяет права, но находится в браузере и не является защищённой средой. В демо можно просмотреть его данные через инструменты разработчика.
Сервер обязан заново проверить сессию, роль, область бригады, принадлежность каждого фото, expectedVersion и допустимость состояния.
Не доверять role, authorId, reviewerId, actualWorkerIds или данным UI как доказательству полномочий.
Идемпотентность и связанные изменения отчёта/реестра должны сохраняться атомарно в общей базе, а не только в памяти.
IndexedDB хранит Blob и ключ под [scope,userId,taskId,kind]. Это локальные черновики, не вторая серверная база.
В шаблоне нет service worker и полной офлайн-карты. Холодный запуск без сети не заявлен.

ПОРЯДОК ОБЪЕДИНЕНИЯ
Участник 1 подтверждает общий контракт и React/Vite-каркас.
Участник 3 подтверждает перечисленные тела запросов, auth, ссылки фото, сохраняемые версии и реальные ограничения.
Участник 2 предоставляет общую оболочку/стили и отображение согласованной схемы, подключает обновления карты после приёмки.
Изменения интегрируются Git-коммитами/PR без копирования папок между ветками. Приёмка: tools/worker-demo/qa/acceptance.txt на реальном API и телефоне.
Базу, административную панель, планировщик и редактор проекта этот модуль не дублирует.
